1. 为什么先 Redis 预扣，再落库？
    

核心是把高并发热点从 MySQL 挪到 Redis，先做“快速准入”，再做“最终记账”。

Redis incr/Lua 是内存原子操作，能在毫秒内拒绝超额请求，避免数据库行锁竞争、死锁和连接池打满。

数据库仍是最终事实源，Redis 是流量闸门和并发削峰层。

**库存扣减主流程（****锁单****阶段）**

1. 先走规则校验：活动可用、用户限购、队伍是否可参与。
    
2. 对“老团”先做 Redis 抢占：incr 预占名额，快速拦截并发，避免直接打爆 DB。（_* 1. 使用 Lua 脚本保证"INCR+检查库存+加锁"的原子性_ _* 2. 如果 SETNX 失败，自动回滚库存DECR，避免库存泄漏_）
    
3. 再落库事务：
    
    1. 老团：lock_count = lock_count + 1 where lock_count < target_count（条件更新防超卖）
        
    2. 新团：创建团单，初始 lock_count = 1
        
    3. 写入拼团明细单。
        
4. 返回锁单成功，等待支付结算。
    

**支付后（结算阶段）**

1. 明细单状态从“锁定”改“已支付”。
    
2. 团维度 complete_count + 1。
    
3. 达到目标人数后，把团状态改完成。
    

**失败与补偿**

1. 如果落库失败，立即做库存恢复（回补 Redis 恢复计数）。
    
2. 退款时反向回滚名额（未支付退单回滚 lock_count，已支付退单回滚 lock_count/complete_count）。
    

3. 数据库失败时怎么补偿？
    

- 即时补偿：捕获异常后立刻回补库存（现在是记 recovery 量）。
    
- 延迟补偿：落一条“补偿任务”表，后台重试，直到成功或人工介入。
    
- 不确定结果补偿：如果调用超时/连接中断，先“查单”判断 DB 是否成功，再决定是否补偿，避免误回滚。
    
- 生产上建议加补偿状态机：INIT -> RETRY -> DONE/DEAD，并加告警。
    

4. 为什么要异步预加载？用 CompletableFuture 怎么编排？
    

- 试算依赖是并行可取的（活动配置、SKU、标签等），串行会把 RT 拉成“各依赖耗时之和”。
    
- 异步预加载把延迟变成“最长那条依赖”的延迟，提升吞吐和 P95/P99。
    
- 编排建议：supplyAsync 并发拉取 + allOf 汇聚 + orTimeout 超时 + exceptionally 降级。
    

5. 怎么限流？
    

网关层：全局 QPS/突发流量控制。

接口层：按 userId/IP 限频（你当前已有注解限流）。

业务层：按 activityId/teamId 热点限流（令牌桶/信号量）。

下游保护：线程池隔离 + 超时熔断。

- 关键是“限流 + 降级 + 动态开关（DCC）”联动，不是只返回 429。

## 难点

高并发拼团项目中，秒杀时段库存抢占的性能瓶颈突出。初期用数据库行锁导致并发量超 500TPS（每秒事务数） 就卡顿，改为 Redis 无锁化方案后，又出现缓存与数据库库存不一致问题。通过 “预扣减 Redis 库存 + 异步确认数据库 + 定时对账补偿” 机制，结合 BitMap 快速过滤无效用户，最终支撑了 5000+TPS 的峰值，库存偏差控制在 0.05% 内

## DDD

1. 你用了DDD，讲一下DDD的优势？
    

- 面向对象设计，数据行为绑定，告别贫血模型；
    
- 降低复杂度，分而治之；
    
- 它通过边界划分将复杂业务领域简单化，帮我们设计出清晰的领域和应用边界，可以很容易地实现业务和技术统一的架构演进；
    

2. 什么是充血模型？
    

**充血模型**，指将对象的属性信息与行为逻辑聚合到一个类中。

3. 你项目中的DDD具体怎么设计的？
    

DDD能有效解决复杂业务逻辑的拆解问题，通过业务场景分析，划分出活动域（管理拼团规则）、标签域（用户画像和权限v过滤）、交易域（订单和结算）。例如，拼团锁单流程属于交易域，而人群标签过滤属于标签域。

4. DDD领域划分的依据？
    

- 每个领域的业务规则互相不交叉。（如拼团的 “成团人数要求”、标签域的 “权限过滤逻辑”）
    
- 划分后需满足 “域内高内聚、域间低耦合”，即一个领域内的业务逻辑、数据、行为高度关联，跨领域的依赖和交互尽可能少
    
- 领域划分需考虑**数据**的归属与**关联**：同一领域内的领域模型（如实体、值对象）应共享关联数据，不同领域的数据应尽量独立，避免跨域频繁访问数据导致性能问题或数据一致性风险。
