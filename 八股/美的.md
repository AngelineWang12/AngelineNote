
1. 你所在模块的业务定位是什么？
    

这个服务整体更偏制造园区/工厂内部业务管理这一类。里面会按领域拆成几个部分，比如运营类、制造执行类、组织和园区主数据类。我当时主要接触的是 MES 这一块，更贴近库存执行、库存流转这类业务。

2. 模块上下游分别是谁？
    

如果从技术入口看，上游主要是前端页面请求、部分公共接口调用，以及少量定时任务和消息消费。

如果从业务链路看，我负责的库存转移/库存属性转移，通常是由入库、仓储整理、出库准备这类仓内作业场景触发；下游主要影响的是库存主数据、库存流水、转移单据，以及货位、托盘这类仓储对象。

  

3. 库存转移解决的真实物理场景是什么？
    

我们当时抽象的仓内场景主要有入库区、货架区和出库区。

一个比较典型的场景是空托盘转移：出库之后会沉淀很多空托盘，而入库时又需要托盘承载货物，所以需要把出库区的空托盘转到入库区。

另外还有普通的库存转移，也就是物料在不同货位之间移动；以及理库合托，就是把两个货位上的物料整理合并到一个货位上。

4. 三种库存转移分别是什么？
    

空托盘转移、库存转移和理库合托

5. 库存属性转移四种类型分别是什么？
    

主要有四种：物料转物料、订单转订单、订单转共享、共享转订单。

本质上就是两类变化：一类是物料属性变化，一类是库存归属变化，比如从订单专属库存转成共享库存，或者从共享库存重新归属到某个订单。

6. 为什么用策略模式？
    

因为不同转移类型的前置校验条件不一样，真正落库时要修改的数据也不一样。

如果全部写在一个大方法里，会变成很长的 if-else，后面扩展新类型也很难维护。

所以后来把每种转移类型拆成独立策略实现，把校验和处理逻辑分开，这样更清晰，也更符合开闭原则。

7. 涉及哪些表？核心字段有哪些？
    

我这块主要会涉及两类数据：

一类是库存主表，用来标识具体是哪一批、哪种物料、在哪个货位上的库存；

另一类是托盘相关的绑定关系数据，用来维护托盘在转移过程中的关联状态。

对库存来说，比较核心的维度是物料编码、货位编码和批次号；托盘这边则会维护托盘和当前业务对象之间的绑定关系。

8. 批次号冲突问题是怎么产生、定位、修复的？
    

批次号原来是 12 位，前 6 位是日期，后 6 位是流水号。正常入库时，这个流水号是从 Redis 里取当天序列来保证递增的。

但库存属性转移是对已有库存做二次生成，当时生成新批次号时走的是数据库里“当天最大批次号 +1”的逻辑，没有和入库共用同一套 Redis 序列。

这样一来，如果属性转移发生在当天，同时又有新的入库单生成批次号，两边序列来源不一致，就可能撞号。

后来我们的处理思路是把批次号扩展两位，属性转移不再去竞争原来的主流水号，只在末两位上做区分，这样把入库生成和属性转移生成隔离开了。

## 难点

**难点一：库存转移的并发安全**

- 背景：库存转移涉及多表、多工厂数据，存在高并发更新的情况。
    
- 难点：如何保证并发下的数据一致性，避免超卖或脏数据。
    
- 解决：我采用了 Redisson 分布式锁，配合事务管理，确保多表数据强一致性。同时通过观察者模式驱动库存变更事件，降低模块间耦合。
    
- 收获：掌握了分布式锁在并发业务中的应用场景与局限。
    

**难点二：批量导入的性能与校验**

- 背景：设备停线和出勤信息需要批量导入校验。
    
- 难点：数据量大，逐条校验会拖慢系统响应。
    
- 解决：我将校验结果放入 Redis 缓存，并对唯一性约束做了批量校验，提升了整体效率。

## 为什么采用观察者模式而不是mq

观察者模式解决的是进程内的代码解耦，追求强一致性；而MQ解决的是分布式的系统解耦，追求最终一致性和削峰填谷

1. **首先是事务一致性：** 在美的这个库存场景中，后续的动作（如记录流水、状态联动）和库存扣减在业务上属于**原子操作**。使用 Spring 的观察者模式（ApplicationEvent），可以让监听器的逻辑在**同一个数据库事务**中执行。一旦发生异常，可以利用 Spring 的事务传播机制整体回滚，确保账实相符。而如果使用 MQ，就会引入分布式事务的复杂性，在这个场景下属于过度设计。
    
2. **其次是架构轻重：** 这部分业务更多是模块内的逻辑解耦，而不是跨服务的通信。观察者模式是**进程内**的通信，没有网络开销，延迟极低。
    

那如果观察者里的逻辑执行很慢，阻塞了主线程怎么办？” **回答：** “Spring 的 `@EventListener` 可以配合 `@Async` 注解使用，瞬间变成异步执行。如果业务逻辑确实耗时且不需要强事务一致性（比如发短信通知），我会加上 `@Async` 让它在线程池中跑，或者这时候再考虑升级为 MQ。”

## 项目线程池怎么实现的

线程池用法，包括参数、拒绝策略、注意事项等

实习项目：

```Java
int corePooSize = 20;           // 核心线程数
int maximumPoolSize = 200;      // 最大线程数
int keepAliveTime = 60;         // 空闲线程存活时间
TimeUnit unit = TimeUnit.SECONDS; // 时间单位
BlockingQueue<Runnable> workQueue = new ArrayBlockingQueue<>(10); // 任务队列
ThreadFactory threadFactory = Executors.defaultThreadFactory();   // 线程工厂
RejectedExecutionHandler handler = new ThreadPoolExecutor.CallerRunsPolicy(); // 拒绝策略
```

项目采用 CallerRunsPolicy 拒绝策略：

- 当线程池和队列都满时，新提交的任务将由调用线程（提交任务的线程）直接执行
    
- 这种策略可以减缓新任务的提交速度，但不会丢弃任务
    

任务队列：`ArrayBlockingQueue`是有界队列，有助于防止资源耗尽

注意事项：

- 队列容量较小，可能频繁触发拒绝策略
    
- 线程池参数需要根据实际业务负载进行调优
    

## 项目中反射的应用

在项目中，我们使用反射机制主要是为了实现通用化的功能处理。例如在一个租户编码自动设置的 AOP 切面中，通过反射动态解析类和方法上的 @RequestMapping 及其派生注解（如 @GetMapping）来获取请求 URL，判断是否为非登录态接口；同时反射遍历方法参数的 @RequestParam 注解，提取租户编码参数；对于请求体中的对象（包括集合、分页对象等），通过反射递归访问其属性（包括私有属性和父类属性），通用地获取租户编码字段。这样做的好处是解耦了切面逻辑与具体的接口参数、对象类型，无需针对每种场景硬编码，让代码更通用、可扩展，这也是反射在动态处理注解、参数和对象属性时的典型应用。

## 我们在调用链的深处（比如 Service 层或 AOP 切面），是如何拿到“当前登录用户”这个信息的？

LoadRoleAspect

在我的项目中，这两种方式其实都有涉及：

1. **关于隐式传递：** 我们后端使用了 **ThreadLocal** 来实现请求上下文的透传。在请求进入拦截器时，会解析 Token 并将用户信息绑定到当前线程的 ThreadLocal 中（也就是代码中的 `MideaAuthService`）。这样在 Service 层或 AOP 切面中，不需要在每个方法参数都传递 User 对象，直接通过上下文获取即可，解决了参数列表冗余的问题。
    
2. **关于显式传递：** 但在具体的业务逻辑处理上，为了保证数据流的清晰，我使用了 AOP 切面。切面从 ThreadLocal（隐式上下文）中获取用户身份，加载权限数据，然后**注入到业务** **DTO** **参数中**。 这样做的好处是：**业务 Service 方法依然保持纯洁，只依赖入参 DTO**，这样单元测试更容易写，不用为了测试一个 Service 方法而去 Mock 复杂的 ThreadLocal 上下文。”
    

TenantCodeSetAspect

它是从**HTTP请求****参数**中通过**反射**“硬抓”出来的，然后通过 **`ShardingHintHelper`****（通常基于 ThreadLocal）** 隐式地传递给底层的数据库中间件。

## 你是怎么配置线程池参数的？依据是什么

关于参数配置，我们要结合业务类型来看。

1. **业务类型判断：** 我们的业务主要是 Web 后端接口，涉及大量的数据库查询、Redis 交互以及 RPC 调用，线程大部分时间处于 **‘等待（Blocking）’** 状态，所以这属于典型的 **IO** **密集型** 场景。
    
2. **具体配置：** 如果是 CPU 密集型，通常是 N+1；但因为我们是 **IO** **密集型**，所以我参考的经验公式是 **2N**（N为CPU核数）甚至更多。 在项目中，我们将 **核心****线程数****设置为 20**（保证日常流量的处理），**最大线程数设置为 200**（应对突发的高并发流量，防止请求堆积）。这个 200 是根据我们在压测时观察 CPU 利用率和接口响应时间推算出来的合理值。
    
3. **执行流程：** 当一个任务提交时，线程池的处理流程是：
    
    1. 首先看**核心线程**满没满，没满就创建线程执行；
        
    2. 如果满了，就丢进**阻塞队列**（我们一般用 `LinkedBlockingQueue` 并设置界限，防止 OOM）；
        
    3. 如果队列也满了，就会开启**非核心线程**直到达到最大线程数（200）；
        
    4. 如果连 200 个线程都在忙，队列也满了，就会执行**拒绝策略**（比如默认的 `AbortPolicy` 抛异常，或者 `CallerRunsPolicy` 由调用者自己执行）。
        
    
      你刚才提到队列，队列的大小你们设了多少？如果不设置大小会怎样？”
    
      **回答：**
    
    > “队列大小必须设置（比如设置 1000 或 2000）。 如果使用默认的 `LinkedBlockingQueue` 构造函数，它的长度是 `Integer.MAX_VALUE`（约等于无界）。 这样的话，**最大****线程数****（maximumPoolSize）参数就会失效**（因为队列永远装不满，永远不会去创建临时线程），更严重的是，如果请求积压太多，会导致 **OOM****（****内存****溢出）**。”
